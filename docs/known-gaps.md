# Trimix — Known Gaps (Stage-5 slice, as of 2026-07-03; aggregator pivot 2026-07-05)

Honest record of what the vertical slice does NOT fully do, so nothing reads as shipped-when-it-isn't. The slice passed its gate (0-error build, 169 tests, signed APK, backend-on-real-Postgres); these are the deliberate edges of that scope.

**Production-wiring release gate PASSED (2026-07-06):** fast-path build 0 errors; **454 Core + 79 Api tests green** (447→454 after the connector-purge identity-change + startup-reconciliation fixes below); signed Android **APK + AAB** (34 MB, `net.frostaura.trimix-Signed.{apk,aab}`); backend migrate-from-zero applied all 5 migrations on a clean Postgres 17 with `/api/v1/healthz` → `{"status":"ok","db":"ok"}` (HTTP 200). The four production-wiring surfaces (real export sink, connector activation UI + consent, real BLE GATT pipeline, production Apple/Google receipt validation, config/secrets, privacy purge) are now REAL code — see [`docs/production-readiness.md`](production-readiness.md) for the REAL vs REAL-needs-data vs RUNTIME-GATED split and the per-input config keys. The items below are the surviving honest edges.

## Production-wiring hostile-QA pass (2026-07-06)
Adversarial review of the just-added production surface (real export sink, connector activation, real BLE GATT, server receipt validation, config/privacy). Fixed this pass (with tests): **iOS receipt overflow (critical)** — Apple StoreKit bundle receipts are multi-KB and overflowed the `varchar(2048)` unique `Receipts.Token` column / btree key, so every real iOS purchase+restore would have 500'd with no entitlement; `Token` is now unbounded `text` and uniqueness rides a fixed-length `TokenSha256` hash (`ReceiptTokenHash`, migration `WidenReceiptToken`, verified applying on real Postgres). **Connector master-switch was inert (high)** — `Features.EnableCloudConnectors`/`EnablePushConnectors` had no consumer, so reverse-eng cloud connectors (with live in-source vendor endpoints) were one consent-tap from going live despite the flag being false; the flags are now a real **registration gate** (`AddTrimixCore` skips the family unless its flag is on, wired from `appsettings.json` via `TrimixCoreOptions`), so a disabled family never surfaces in Connected accounts, can never be consented, and sync can never pull it. **GDPR delete never called the server (high)** — see GDPR/CCPA section. Also fixed: Android BLE wrote the notification CCCD value even for indicate-only characteristics (medium); the receipt insert-conflict catch was over-broad (now rethrows non-conflict `DbUpdateException`s instead of a misleading 500); plaintext password could linger on a cloud-connector singleton's early-return paths; iOS dropped a configured handshake when write+notify lived in different GATT services; vendor name-hint matching used unbounded substring (now word-bounded, so "Lantern" no longer matches "Tern"); backend base `appsettings.json` no longer ships a committed DB credential (moved to `appsettings.Development.json`, with a fail-closed startup guard).

- **RESOLVED (2026-07-06) — connector purge now fires on IDENTITY CHANGE, not just the sign-OUT edge.** `AuthSession.SignInAsync` now tracks the last REAL account established on this device (`SecureStoreKeys.LastAccountId`, written on sign-in, NOT cleared on sign-out, held in the secure enclave so it survives uninstall in lockstep with the connector tokens it guards) and raises a new `IAuthSession.IdentityChanged` event **only** on a genuine account→different-account switch. `ConnectorPurgeService` subscribes to it (alongside the existing `AuthStateChanged==false` backstop) and purges the previous identity's device-global connector consent+tokens — closing the shared-device handoff (guest connects a vendor, then a *different* account signs in without an intervening sign-out). The dominant **guest→account upgrade is preserved as single-user continuity** (no prior established account ⇒ no `IdentityChanged` ⇒ connectors KEEP). Tests (`Trimix.Core.Tests/Privacy/ConnectorPurgeServiceTests.cs`, over the REAL `AuthSession`): `Guest_to_account_upgrade_keeps_connectors`, `Account_switch_purges_the_previous_identitys_connectors`, `Same_account_re_sign_in_keeps_connectors`; sign-out still purges (`Sign_out_purges_consent_and_every_token_for_all_connectors`).
- **RESOLVED (2026-07-06) — purge is now AWAITED in the flow + a startup reconciliation retries an interrupted one.** (a) `SettingsViewModel.SignOutAsync`/`DeleteMyDataAsync` now `await IConnectorPurgeService.PurgeAllAsync()` within the flow (extracted `IConnectorPurgeService`; registered in `AddTrimixCore` as one singleton), so completion is guaranteed instead of left to a fire-and-forget event continuation an app teardown could interrupt; the automatic `AuthStateChanged` subscription remains as an idempotent backstop. (b) `AppStartupService.RunAsync` runs `PurgeAllAsync` once on any **unauthenticated** launch (guarded off the authenticated sync path so it never disrupts a signed-in launch), clearing any consent/token stranded in the secure enclave (which survives uninstall on iOS) by an interrupted purge. Tests: `Trimix.Core.Tests/SettingsViewModelTests.cs` (`SignOut_awaits_the_connector_purge`, `DeleteMyData_signed_in_erases_server_side_then_signs_out` asserts the purge count, and the server-erasure-failure path asserts **no** purge); `Trimix.Core.Tests/AppStartupServiceTests.cs` (`Unauthenticated_startup_reconciles_by_purging_connectors`, `Authenticated_startup_syncs_and_does_not_purge`, `Interrupted_purge_is_retried_on_next_unauthenticated_startup` — a flaky secure-token store strands a token on the first sweep, cleared on the next unauthenticated startup).

## Aggregator pivot — legal & runtime gaps (2026-07-05, founder-directed)
The import layer is being re-architected from BLE-only to a multi-source hub (see PRD Amendments set 2 + `design/aggregator-architecture.md`). The honest edges of that work:

- **No clean vendor cloud API exists.** Vendor-cloud **pull** (Garmin `garth`, Suunto/Oceanic private sync) and cert-agency **push** (PADI, SSI) have no published/partner API and are built by **reverse-engineering credential-gated backends** — a ToS/CFAA-gray-area that **knowingly fails gate-3 "integrated legally."** Shipped as real features per **founder-directed override (2026-07-05)** after the risk was flagged. Guardrails held: no plaintext vendor passwords (token in secure storage), per-user opt-in + disclosure, truthful labeling. This is a *documented, accepted* legal risk, not an oversight.
- **Reverse-eng connectors are not live-verified here.** Their HTTP clients are built against a testable transport abstraction with recorded fixtures; they are **not** (and must not be) exercised against real vendor production servers from this environment. Live validation + legal sign-off precede any store listing.
- **Apple HealthKit source** is real code, **runtime-gated**: needs a physical iOS device + an Apple Watch Ultra / Oceanic+ writing `underwaterDiving` data; the iOS Simulator cannot exercise it. Compile-verified only here (net10.0-ios also not build-verified on this beta-macOS host — carried over from the BLE gap below). Compliance artifacts are now declared: `NSHealthShareUsageDescription` (Info.plist), the `com.apple.developer.healthkit` entitlement (Entitlements.Device.plist, device build only), and Health/Fitness collected-data types in `PrivacyInfo.xcprivacy`. **Remaining device gap:** the signing provisioning profile must enable the HealthKit capability (paid-provisioning / name-clearance track) before a device or store build.
- **SSI push sends credentials as GET query params** (`SsiPushDestinationConnector`), not a POST body like PADI — the endpoint shape is dictated by SSI's reverse-engineered private DiveSSI backend. The connector ships DARK and never persists the password (token-only), so no guardrail is violated, but query-string credentials can surface in intermediary/proxy logs. Hardening (POST body if the vendor path allows, or guaranteed no request-URL logging on this transport) is deferred to the legal-override live-integration track.
- **Real BLE protocols** (Suunto, ScubaPro added to Shearwater) are clean-room C# behind the vendor abstraction, **fixture-tested** but **not field-validated** — same M3 real-hardware kill-line as before, inherited by the pivot, not removed. Mares remains highest-risk; Garmin is FIT-file/cloud only (not BLE).
- **PADI/SSI push fidelity is lossy.** SSI QR carries summary only (no profile/site); PADI has no structured write. The reliable, honest destination is diver-controlled **UDDF/DL7/PDF export**.

## Deferred by design (post-slice)
- **Real dive-computer BLE protocol.** The slice imports via `SimulatorTransport` + a Shearwater *fixture-frame* parser. The frame format is our simulator contract, **not** the real Shearwater BLE protocol — real-hardware field validation (post-dive, salt-water, low-signal) is the open **M3 risk** and the core kill-line (≥2 of 4 vendors must work). The **real GATT pipeline is now wired** (2026-07-06 production wiring): Android `BleTransport` (Android.Bluetooth.LE) + iOS `BleTransport` (CoreBluetooth) do a real connect → discover service → subscribe notify → frame → handshake, with vendor identification by advertised service-UUID/name (`BleGattProfiles`) and deploy-time UUID/handshake overrides (`BleGattOverrides` ← config). **Compile-verified on both platforms; not runtime-exercisable here** — the iOS Simulator has no Bluetooth radio (`CBManagerState.Unsupported`), so real BLE needs a physical device + a real computer. **Only Shearwater's service UUID is pinned as public fact** (`fe25c237-…`, libdivecomputer/Subsurface); Suunto/Garmin/Mares/Oceanic are name-hint-only with null service UUID and their handshake bytes are **labelled deploy inputs (`Ble:<Vendor>:HandshakeCommandsHex`), never guessed** — none is presented as verified. Garmin is FIT-file/cloud only (not BLE).
- **Store billing against a live listing.** `SandboxBillingService` is the slice's live purchase path (Debug default, both platforms) and is fully exercised end-to-end (purchase → HMAC receipt → server validation → entitlement → restore). Real store clients exist Release-only and **compile-verified**: Android `PlayBillingService` (Xamarin.Android.Google.BillingClient) and iOS `StoreKitBillingService` (StoreKit 1). **Production server receipt validation is now REAL (needs data), not a TODO** (2026-07-06 production wiring): `AppleAppStoreReceiptVerifier` calls Apple `verifyReceipt` (prod→sandbox 21007 fallback, `status==0` + bundle-id + `product_id` checks, fail-closed) and `GooglePlayApiReceiptVerifier` does a service-account JWT→OAuth2 exchange then `purchases.products.get` (`purchaseState==0`), both through an injectable `HttpClient` (unit-tested against mocked handlers, no real network in CI). Both **ship DARK** — empty billing config ⇒ `NotConfigured` ⇒ endpoint 501, preserving the sandbox path — until the store credentials in `docs/production-readiness.md §Surface 5` are supplied. Real store purchases still need App Store Connect / a Play listing (blocked on **name clearance**) or a local `.storekit` config (`Platforms/iOS/Trimix.storekit`) for a real device receipt. Forward note: the Apple verifier matches the StoreKit-1 client; a StoreKit-2 client migration would switch it to the App Store Server API (ES256 JWT + JWS).
- **Passkey (WebAuthn) sign-in — the only account auth.** Email/password + OAuth are **removed**; accounts are created and signed into with a platform passkey. Full stack is implemented + compile-verified: iOS `ASAuthorizationPlatformPublicKeyCredentialProvider`, Android Credential Manager (`androidx.credentials`), and a backend **Fido2NetLib** relying party (`PasskeyEndpoints`, `PasskeyCredential` + `Passkeys` migration, `.well-known/{apple-app-site-association,assetlinks.json}` served from `Passkey:*` config), keeping the frozen `account_created` funnel event. **Runtime is domain/entitlement-gated and cannot be exercised on a simulator/emulator against localhost**: passkeys require the app associated with a real HTTPS relying-party domain — iOS `associated-domains` entitlement (`webcredentials:<rpId>`, in `Platforms/iOS/Entitlements.plist`, applied to the **device** build only) + a paid Apple Developer signing/provisioning, and Android **Digital Asset Links** (`assetlinks.json` matching the app-signing SHA-256). To go live: set `Passkey:RelyingPartyId`/origins, host the two `.well-known` files on the RP domain, and register the entitlement + signing cert. Passkeys need iOS 16+ / Android 9+ (older OS → guest only).
- **Name clearance.** "Trimix" is founder-picked but flagged high-collision-risk in dive software. Store + `.com`/`.app` + USPTO (Class 9/42) re-check is a **blocking gate before any public listing, domain, or trademark** — and transitively blocks the real store-billing path above.
- **Site-DB seed licensing.** 64 seeded sites are honest approximations of publicly-known values, fine for a slice. A legally-licensed seed dataset remains a **launch blocker** per the PRD.
- **iOS.** The `net10.0-ios` TFM is retained and intended to compile, but is **not build-verified** on this host (beta macOS 27 + Xcode 26.6 toolchain risk). Android is the proven target.

## GDPR/CCPA
- Server-side privacy **export** and **delete** endpoints exist (`PrivacyEndpoints.cs`, `ApiRoutes.Privacy`). As of the production-wiring pass (2026-07-06) the client **calls the live `POST /privacy/delete`** for a signed-in user (`SettingsViewModel.DeleteMyDataAsync` → `IApiClient.DeleteMyDataAsync`) BEFORE sign-out, so the account, analytics, receipts, entitlement, contributions, and synced dives are all hard-deleted server-side (not just local dives); on a server failure it surfaces an error and does NOT sign out, so erasure is never silently skipped. Covered by `SettingsViewModelTests`. Erasure deletes analytics by the account's device **pseudo-id(s)**, not only `UserId`, so pre-auth / guest funnel rows (`install`, `first_run_completed`, `dive_logged_*`, ingested with `UserId=null`) are erased too and the returned count is truthful — covered by `PrivacyTests.Delete_also_erases_pre_auth_guest_analytics_keyed_only_by_pseudo_id`.
- **Deferred — export omits connector state.** GDPR/CCPA **export** (`SettingsViewModel.ExportDataAsync` + server `PrivacyExportResponse`) serializes account + entitlement + dives + analytics count, but NOT the diver's connected-vendor list / per-connector consent flags. The erasure path treats that linkage as personal data (it wipes it), so export coverage is asymmetric. Low impact today (connectors ship dark / not registered by default) — add a token-free `connectors` section (id, display name, consented, connected) to close it. No secret is exposed (token material is never exported).
